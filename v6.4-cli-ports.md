## Issues

### #41 up --tmux drops --port for the dashboard window

## Problem

`factory up --tmux` starts a watcher window and a dashboard window, but a `--port` given to `up` never reaches the dashboard. The dashboard binds the default port while the operator expects their own, and the printed attach hint is then wrong.

## Acceptance

- `factory up --tmux --port 4200` starts the dashboard on 4200.
- The watcher window is unchanged.
- A test proves the dashboard window receives the port, and fails when the forwarding is removed.

## Out of scope

- Choosing a free port when the default is taken: #159.

### #159 Pick a free dashboard port when 4100 is taken

## Problem

Two factories on one machine both ask for the default dashboard port. The second dashboard fails to start with a bind error instead of giving the operator a usable port.

## Acceptance

- With the default port taken and no port given, the dashboard starts on the next free port and prints its address.
- With an explicit port that is taken, it exits with a one-line error naming that port. It never moves to another port silently.
- A test covers both cases without opening a real socket, and fails when the fallback is removed.

## Out of scope

- Changing the default port. Forwarding `--port` through `up --tmux`: #41.

### #616 factory up treats --help as a start request

## Problem
Running `factory up --help` does not print usage. It starts the watcher and keeps running, so a person reading the usage can start a second long-running process by accident.

## Acceptance
- `factory up --help` and `-h` print the usage and exit without starting anything.
- The same holds for every subcommand that starts a long-running process.
- A test runs each such subcommand with `--help` and asserts it exits within a few seconds.

## Out of scope
- Changing which flags the commands accept.
