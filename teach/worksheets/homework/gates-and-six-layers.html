Gates and the six layers

Build the gates and six layers an agent needs before it runs alone

A blueprint tells an agent how to work. It does not stop the agent when it ignores the blueprint. The six layers are the parts that do: a boundary, a place to run, routed context, stage skills, verification and delivery. Then each task type from how we work today gets its own gate.

Six layers answer six questions before an agent touches a repo

A layer is one part of the factory that answers one question about unattended work. Today a person answers all six in their head. The factory answers each one in a file or a script.

Boundary stops an edit before it lands, then checks the diff again

The Boundary layer decides what a stage may touch unattended. A hook can miss a sed -i run through Bash. So the runner diffs the branch against protectedPaths before every push.

Execution gives every issue its own worktree, budget and clock

The Execution layer decides where an agent runs and what it can reach. Today Claude Code runs in Param's main checkout, on main. The factory claims an issue, makes a worktree for it, and kills a stage that runs past its budget.

All three repos add this by installing the factory. Nothing is built per repo, except the englishmaa E2E ports, which repo.json already names.

Context reaches the agent from the issue and the repo, never from a laptop

The Context layer decides what a stage knows. A stage reads the issue, the handoff from the last stage, AGENTS.md and any rule whose path it touches. Anything on Param's laptop is invisible to it.

What to add AGENTS.md in kaas.team and lwp-academy, and a one-line CLAUDE.md in all three. Without them a stage starts from the issue alone.

Skills give each stage one job and one shape of output

The Skills layer holds the reusable know-how of each stage. The factory template ships one skill per stage. A stop hook checks that each stage wrote its artifact in the shape the runner expects.

The vendored skills from the blueprint plug in here: triage, systematic-debugging and code-review-and-quality sit beside the stage skills in .claude/skills.

Verification trusts the gate's own line, never the agent's claim

The Verification layer decides what proof exists before a human looks. The runner reads one line that gates.sh prints. Then verify reverts the fix, and the new test must fail without it.

Delivery ends at a PR and a human merge, because main deploys

The Delivery layer decides how work reaches a person and who ships it. All three apps deploy from main. So the factory stops at a PR, and a human merges.

What to add ci.yml in kaas.team and lwp-academy. Branch protection needs a paid plan on these private repos, so CI is our required check by habit, not by setting.

Each task type gets a gate that matches what can go wrong with it

A gate is a command that can refuse a change. One gate for everything is too weak for a security bug and too slow for a copy edit. These are the gates we build for the task types we run by hand today.

Dependabot PR: merge-ready means green and in the patch range

Vulnerability alert: no dismissal without a reason and a date

Security bug: the test must fail on the old code

Lighthouse: the same bar in all three repos

UI task: a preview before production, and a human says yes

A gate counts only when a mutation proves it can fail

A mutation breaks the code on purpose to show a check catches it. The factory repo lists one per check in tests/mutations.json, and make check-mutations runs them in CI. Every gate on this page lands the same way, in the same change.

Key terms

Layer
One part of the factory that answers one question about unattended work.
Boundary
What a stage may touch: protected paths, deny rules and the diff check.
Gate
A command that can refuse a change, read by the runner from one line.
Test that bites
A test that fails when the fix is reverted.
Mutation
A deliberate break that proves a check can fail.
