The factory loop turns a labelled issue into a PR a human merges

The factory runs triage, plan, build, verify and PR with no one at the keyboard. The runner, not the agent, decides green or red.

Compare it with how we work today: a human still labels, approves and merges, and every step between now has a check.

Dogfood the factory on your own product first

Dogfooding means running your own tool on your own product first. We ran 35 issues overnight on our product apps.

35issues run overnight
30shipped
5cancelled by the operator
29verify rejects, against 24 passes

More rejects than passes is the tester doing its job: most cards needed a second build.

Every failure the factory hits becomes an issue against the factory

Every fault seen in a run is filed against the factory, fixed with a test, and released to every repo.

Installing it is three commands per repo, after the blueprint and gates exist

The template is the hooks, stage skills and gate script the factory copies into a repo.

factory install ~/learn/kaaslabs/kaas.team        # template: hooks, stage skills, gates.sh
factory init --repo-dir ~/learn/kaaslabs/kaas.team  # .factory/config.json from the stack
factory watch --repo-dir ~/learn/kaaslabs/kaas.team # poll and drive the loop

Any coding agent can run a stage, but only Claude gets the path guard

A preset tells the runner how to call one agent CLI: Claude, Codex, Gemini, OpenCode, Cursor, Pi or Mastra Code. Put a different vendor on verify than on build, so the tester does not share the builder's blind spots.

{
  "agents": { "claude": { "preset": "claude" }, "gemini": { "preset": "gemini" } },
  "stages": { "default": "claude", "verify": "gemini" }
}

Key terms

Software factory
A runner that takes an issue to a PR through checked stages.
Dogfooding
Running our own tool on our own product first.
Template
The hooks, stage skills and gate script copied into each repo.
Route
The rule that sends a task type to the factory, a human, or both.
Preset
How the runner calls one agent CLI for a stage.
