Map how one change reaches production

Answer in your own words. Bullets, a short table or notes pasted in Markdown all work. Write what a new teammate would need to know, not everything you know.

1Where does work come from, and what checks it today?

Name the tracker, the team, who reviews, and the checks that run on every pull request.

2Walk one real change from report to production

Pick something merged in the last two weeks. Note who did each step and how long it waited, then name the longest wait.

3Which tickets will you automate first?

Look at the last 30 days. Start where volume is high, risk is low and a check can prove the result. The workflow library shows how each type runs.

4Write your first workflow as stages

For each stage, say what goes in, what comes out, who runs it (a script, an agent or a person) and the check that ends it.

5What makes a change low, medium or high risk?

The change sets the tier, not who wrote it. Low merges on green checks, medium needs one reviewer and high needs two.

6What would an agent need to run this well?

Think of one real issue. What is not written down anywhere? Where should the agent stop and ask? What evidence would let you approve its pull request in ten minutes?
