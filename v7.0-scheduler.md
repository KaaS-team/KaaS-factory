## Order of work, for each issue

1. Check first whether the acceptance already holds on the base branch. If it does, change no code and record the evidence in your report.
2. Write a test that fails, then the code that makes it pass.
3. Run the test file, then `make fast BASE=origin/release/v7.0.0`. Do not run the full `make check`: CI is the full gate.
4. Commit with `git commit -s` (CI rejects a commit without a sign-off), one commit per issue, with the subject ending in `(#N)`. Then `git push -u origin cluster/v7.0-scheduler`. Push after every issue, so a dropped session loses little.

- If one issue is blocked, record why and move on to the next. Do not stop the session for it, and do not widen scope to get around it.

## Issues

### #599 Operator-only issues never dispatch and show as Needs you

## Problem

An issue marked as operator work can still be picked up by the watcher.

## Acceptance

- An issue with `Runner: operator` is never dispatched.
- It appears in the inbox as Needs you.
- A test proves it is skipped and fails when the filter is removed.

## Out of scope

- Other labels.

### #600 The watcher dispatches in the scheduler order

## Problem

The watcher dispatches ready issues by number, ignoring the order the scheduler computes from dependencies.

## Acceptance

- Two ready issues dispatch in the scheduler's order, not number order.
- A test fails when the order is reverted.

## Out of scope

- Changing how dependencies are declared.

Blocked by: #599

### #601 `factory plan-order` prints the order, critical path and reasons

## Problem

There is no command that shows the order the scheduler will use, the critical path, or why an issue is waiting.

## Acceptance

- `factory plan-order` prints the order, the critical path and the reason each waiting issue waits.
- A fixture graph has a golden output test.

## Out of scope

- Changing the order itself.

A check that `make check` does not reach did not ship.

## Out of scope
