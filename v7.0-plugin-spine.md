## Issues

### #587 Plugin registry: one place that agents, steps and trackers register into

## Problem

Agents, step types and trackers are wired by hand in several places, so adding one means editing core files. There is no single registry they register into.

## Acceptance

- A registry holds agents, step types and trackers, each registered by name.
- Core code looks them up by name and does not import a specific one.
- Registering the same name twice fails and names both.
- A test registers a fake of each kind and uses it; it fails when the lookup is bypassed.

## Out of scope

- Loading plugins from disk: see the loader issue.

### #588 Agents and step types read from the registry

## Problem

Agent presets and step types are hard-coded lists. They should come from the registry, so a new one needs no core change.

## Acceptance

- Every shipped agent and step type is registered at startup and read from the registry.
- No core file lists them by name.
- A structural test fails when a core file names a shipped agent.

## Out of scope

- Moving them into separate packages.

Blocked by: #587

### #589 Plugin manifest, loader, machine config and marketplace schema

## Problem

There is no way to add a plugin without changing the factory: no manifest format, no loader, no machine-level setting for which plugins are on, and no schema for listing plugins in a marketplace.

## Acceptance

- A plugin declares its name, kind and entry in a manifest, and an invalid manifest is rejected with the field named.
- The loader registers every enabled plugin at startup.
- Machine config says which plugins are enabled; the default is the shipped set.
- A marketplace entry has a schema checked by a test.
- A test loads a fake plugin from a temp directory and uses it.

## Out of scope

- Publishing to a marketplace.

Blocked by: #587
