## Issues

### #172 Judge mutations on tests that were green at baseline and skip tests the sandbox cannot run

## Problem

The mutation check refuses to run when any test in the project fails on the unmutated copy ("baseline-red"). One test the sandbox cannot run, or one already red for an unrelated reason, blocks every mutation check, so the whole proof is lost instead of being judged on the tests that matter.

## Acceptance

- The mutation check judges a mutation using only the tests the plan names, plus tests that were green at baseline.
- A test that is red at baseline, or that the sandbox cannot run, is skipped and listed in the output.
- If every named test is red at baseline, the check still fails with a clear message.
- A mutation that no baseline-green test catches is reported as surviving.
- Tests cover a red unrelated test, an unrunnable test and the all-red case.

## Out of scope

- Fixing the red tests themselves.

### #581 Report mutations whose anchor moved after a code change

## Problem

A mutation names the code it changes. When that code moves, the mutation silently stops applying, and a check that used to bite no longer does.

## Acceptance

- A mutation whose target no longer matches fails the mutation check by name.
- A test moves a target and proves the failure.

## Out of scope

- Writing new mutations.

### #345 Make check-mutations required and give the nightly a result

## Problem

The mutation check is not a required check, and the nightly run gives no clear result. A mutation can stop biting and nothing blocks the merge. Splitting mutations into shards (spec 501) is not built.

## Acceptance

- A PR cannot merge when a mutation it touches no longer fails its test.
- The nightly run posts one result: how many mutations ran, how many held, which did not.
- Mutations run in shards so a PR runs only the ones it reaches.
- Making the check required is a repository setting. The issue states that step for the owner.

## Out of scope

- Writing new mutations.

### #171 Separate scaffold tests from permanent tests and prune what a change no longer needs

## Problem

Tests written to scaffold a change and tests worth keeping look the same, so the suite only grows. After a change merges nothing prunes the scaffold. Step one, a ledger of test tiers (spec 502), is not built.

## Acceptance

- Each test a plan adds is tagged as scaffold or permanent.
- After merge, scaffold tests the final change no longer needs are listed for removal or removed.
- The number of permanent tests is recorded per run so growth is visible.
- Tests cover tagging and the post-merge prune.

## Out of scope

- Deleting any existing test without the tag.
